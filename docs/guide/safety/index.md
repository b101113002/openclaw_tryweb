# 04｜建立安全的使用邊界

OpenClaw 的能力越完整，錯誤操作可能造成的影響也越大。助理可能讀取檔案、執行命令、控制瀏覽器或向外傳送訊息；這些能力應該依照實際任務逐項開啟，而不是因為「AI 可能用得到」就全部授權。

本課先建立一個實用原則：**誰可以叫助理做事、助理可以接觸什麼、它能做出什麼改變，必須分開思考。**

## 1. 先定義信任邊界

OpenClaw 官方安全模型以單一 Gateway 的受信任操作者邊界為設計基礎。不要把同一個已啟用工具的 Agent 當成能安全隔離彼此敵意使用者的多租戶平台。

如果不同使用者彼此不信任，應考慮分開 Gateway、憑證，並盡可能分開作業系統使用者或主機。群組成員能向同一個 Agent 傳送訊息時，可能共同使用它被授予的工具能力。

## 2. 分開檢查三種權限

| 權限面向 | 要問自己的問題 | 常見控制方式 |
|---|---|---|
| 誰能觸發 | 哪些人能私訊或在群組呼叫助理？ | Pairing、DM allowlist、群組 allowlist、mention gate |
| 能看到什麼 | 助理能讀取哪些對話、檔案、郵件或網頁？ | 工作區範圍、資料來源限制、Session visibility |
| 能做出什麼改變 | 助理能寫檔、刪檔、執行命令或對外傳送嗎？ | Tool policy、執行核准、Sandbox、人工確認 |

只靠提示詞告訴模型「不要做危險的事」並不足以形成硬性安全邊界。需要限制的能力，應盡量透過工具政策、沙箱、權限與網路設定來限制。

## 3. 把外部內容視為不可信輸入

提示詞注入不只出現在公開聊天室。助理閱讀的網頁、電子郵件、文件、附件、貼上的程式碼與日誌，都可能包含試圖操控模型的文字，例如要求它忽略原本規則、揭露機密或執行某個命令。

實務上應做到：

- 讀取不可信文件時，優先使用唯讀、無執行能力的 Agent。
- 不要讓負責閱讀外部網頁或郵件的 Agent 同時持有不必要的 Shell、瀏覽器控制或外傳工具。
- 不要將 API Key、密碼、Cookie 與私人憑證放入 Agent 能讀取的資料夾。
- 任何涉及刪除、寫入、寄送、發布、付款或變更權限的操作，都先要求人工確認。

## 4. 網路與聊天渠道的基本防護

- Gateway 優先保持在本機 loopback；確實需要遠端使用時，使用經驗證的私人通道，而不是直接公開連接埠。
- 私訊使用 pairing 或 allowlist，不要為方便而開放所有陌生使用者。
- 群組只加入必要聊天室；成員範圍較廣時，啟用提及門檻與發話者限制。
- 不公開 Gateway Token、反向代理憑證、瀏覽器遠端控制端點或管理介面。
- 外掛與 Skills 只安裝明確信任且能檢查來源的項目。

## 5. 定期執行安全稽核

設定或權限有變動時，先檢查 Gateway 狀態與安全稽核：

```bash
openclaw gateway status
openclaw security audit
```

需要更深入的檢查時，依官方文件使用深度稽核選項。稽核結果不是「安全保證」；它是協助你發現設定偏移與高風險配置的檢查工具。每個警告都要依部署情境理解，不要為了讓畫面全綠就盲目套用自動修正。

## 6. 入門安全檢查清單

- [ ] Gateway 沒有不必要地暴露到公網。
- [ ] 陌生私訊不會直接觸發工具型 Agent。
- [ ] 群組成員與聊天室範圍是我明確選擇的。
- [ ] 讀取外部內容的 Agent 沒有過度的執行權限。
- [ ] 憑證不在公開 Repository、聊天記錄或不必要的工作區內。
- [ ] 寫入、刪除、對外傳送與其他高影響操作有人工作為確認點。
- [ ] 我知道如何執行安全稽核與撤銷不再需要的連線。
